# zarko1321/bitsy21321

## Resumen

`zarko1321/bitsy21321` es un repositorio de Hugging Face publicado por el usuario zarko1321 (Žarko Petrović) que, según la model card, contiene el código y la infraestructura de entrenamiento de un modelo de lenguaje decoder-only de aproximadamente 505 millones de parámetros denominado internamente "Eather-500M". No se trata de un modelo con pesos preentrenados: el autor indica explícitamente que los pesos se inicializan de forma aleatoria y que el paquete incluye el pipeline completo de tokenizer, preparación de datos, preentrenamiento, fine-tuning conversacional (SFT) e inferencia.

La relevancia del repositorio es, por tanto, educativa y de referencia: sirve como plantilla reproducible para entrenar un modelo pequeño desde cero en hardware de consumo, con soporte documentado para PyTorch sobre ROCm en GPUs AMD (se cita una RX 7800 XT). No es un modelo listo para producción ni un chatbot funcional; el propio autor advierte que alcanzar capacidad útil de código o conversación requiere datos de calidad, cómputo sustancial y evaluación repetida.

La información pública disponible es muy limitada: cero descargas, cero likes, sin licencia declarada, sin idiomas declarados y sin resultados de benchmarks. La ficha siguiente refleja únicamente lo que consta en la model card y en los metadatos del repositorio.

## Arquitectura y entrenamiento

El modelo es un transformer decoder-only de 26 bloques con anchura oculta de 1.280, 20 cabezas de query y 5 cabezas KV (Grouped Query Attention, ratio 4:1), anchura intermedia SwiGLU de 3.584, RoPE para codificación posicional, RMSNorm y atención causal con Flash/SDPA. El vocabulario es un BPE byte-level de 32.000 tokens con pesos de embedding y salida atados. La implementación es en PyTorch puro y es compatible con builds ROCm de PyTorch para GPUs AMD.

El pipeline de entrenamiento consta de cinco fases documentadas: entrenamiento del tokenizer (`tokenizer_train.py`), pre-tokenización a formato binario uint32 con máscara de pérdida (`prepare.py`), preentrenamiento desde cero (`train.py`), fine-tuning conversacional SFT donde solo los tokens del asistente reciben pérdida (`--fine-tune`), y generación (`generate.py`). El ejemplo de la model card usa `seq-len 256`, microbatch 1, acumulación de gradiente 16 y 20.000 pasos con LR 3e-4 para preentrenamiento, y 2.000 pasos con LR 2e-5 para SFT. No se especifican número de tokens de entrenamiento, composición del dataset, ni uso de RLHF/DPO. El proyecto no incluye KV caching, packing-aware attention, curvas de validación/perplejidad, entrenamiento distribuido, cuantización ni exportación de modelos.

## Capacidades

- Generación de texto autoregresiva en el checkpoint que el usuario entrene; el repositorio descargado no incluye pesos entrenados.
- Fine-tuning conversacional SFT con enmascaramiento de pérdida sobre tokens del asistente y token de fin de turno.
- Entrenamiento de tokenizer BPE byte-level a medida (32.000 tokens) sobre corpus propio en `.txt`.
- Pre-tokenización por chunks con máscara de pérdida, apta para corpus que no caben en RAM.
- Ejecución en GPUs AMD mediante builds ROCm de PyTorch, además de CUDA.
- Exportación a un modelo estándar en formato Llama con el tokenizer entrenado, para su uso en Unsloth Studio (modelo reinicializado, no conversión de pesos).
- No dispone de tool calling, function calling, agentes, visión, audio, thinking mode ni capacidades multilingües declaradas.

## Casos de uso

- Formación y docencia en entrenamiento de LLMs: el repositorio permite recorrer de principio a fin el ciclo tokenizer → preentrenamiento → SFT → generación en una sola GPU de consumo, con código legible y parámetros explícitos.
- Reproducción de experimentos a pequeña escala: investigadores pueden variar `seq-len`, `lr`, `grad-accum` y número de pasos para estudiar dinámicas de entrenamiento en modelos de ~500 M sin infraestructura distribuida.
- Entrenamiento de un tokenizer de dominio específico: `tokenizer_train.py` permite construir un vocabulario BPE de 32.000 tokens sobre corpus propio (por ejemplo, código Python/Luau o documentación técnica) antes de preentrenar.
- Fine-tuning conversacional controlado: el formato JSONL de `data/chat.jsonl` y el enmascaramiento de pérdida permiten adaptar un checkpoint preentrenado a un dominio concreto con pares usuario/asistente curados manualmente.
- Prototipado en hardware AMD: el soporte documentado para ROCm en una RX 7800 XT (16 GB) facilita experimentar con LLMs en equipos sin GPU NVIDIA, usando gradient checkpointing y secuencias cortas para evitar OOM.
- Base para experimentos de arquitectura: al ser código PyTorch puro con GQA, RoPE y SwiGLU, sirve como punto de partida para modificar la atención, la normalización o el tamaño del vocabulario y medir el efecto en el entrenamiento.
- Generación de texto condicionada tras preentrenamiento: `generate.py` permite evaluar cualitativamente checkpoints intermedios con prompts libres o en modo chat, útil para seguir la evolución del modelo durante el entrenamiento.

## Requisitos de hardware

- VRAM estimada para inferencia: no disponible de forma explícita; para un modelo de ~505 M en fp32 se requieren aproximadamente 2 GB solo para pesos, más activaciones y caché KV (el proyecto no incluye KV caching, lo que penaliza la generación larga).
- VRAM estimada para entrenamiento: el autor cita 16 GB como referencia práctica (RX 7800 XT), empezando con `seq-len` 128–256 y microbatch 1, con gradient checkpointing activado por defecto.
- GPUs recomendadas: no se especifican modelos NVIDIA; se documenta explícitamente AMD RX 7800 XT con ROCm. Cualquier GPU con ≥16 GB y soporte PyTorch (CUDA o ROCm) es un punto de partida razonable.
- Cabe en GPU de consumo: sí, según la referencia de 16 GB del autor; no se confirma para GPUs de 8 GB.
- Opciones de despliegue: no se documentan vLLM, llama.cpp, Ollama ni TGI. El proyecto usa scripts propios (`generate.py`) y exportación a formato Llama para Unsloth Studio.
- Latencia y throughput: no disponibles.

## Limitaciones y advertencias

- Los pesos se inicializan aleatoriamente: el repositorio es código de entrenamiento, no un chatbot entrenado. Sin preentrenamiento y SFT propios no produce texto útil.
- Un modelo de ~500 M es pequeño para código avanzado y razonamiento; el autor recomienda preentrenamiento amplio en texto general antes de datos específicos de Python/Luau e instrucciones.
- No es una pila de entrenamiento distribuido de escala de producción: carece de KV caching, packing-aware attention, curvas de validación/perplejidad, entrenamiento distribuido, cuantización y exportación de modelos.
- Aumentar `max_seq_len` por sí solo no otorga contexto largo fiable; se requiere entrenamiento y evaluación adicionales.
- El SFT por streaming concatena conversaciones y puede muestrear ocasionalmente a través de límites entre ellas si el dataset no tiene separadores claros.
- El entrenamiento del tokenizer requiere corpus suficiente para alcanzar 32.000 tokens; con datos de juguete hay que reducir `--vocab-size` y `vocab_size` de `config.json` de forma coordinada.
- Los checkpoints del optimizador son grandes y pueden agotar el disco.
- Licencia no declarada: no hay autorización explícita para uso comercial; debe contactarse con el autor antes de cualquier despliegue productivo.
- Solo se debe entrenar con material sobre el que se tengan derechos de uso.
- Sin datos de sesgos, alucinación ni cobertura idiomática, al no existir un modelo entrenado que evaluar.
- La compatibilidad con Unsloth Studio depende de la versión instalada y genera un modelo nuevo reinicializado, no una conversión de pesos.
