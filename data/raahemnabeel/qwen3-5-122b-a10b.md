# raahemnabeel/qwen3-5-122b-a10b

## Resumen

qwen3-5-122b-a10b es un paquete de despliegue publicado por el usuario raahemnabeel que empaqueta el modelo Qwen/Qwen3.5-122B-A10B del equipo Qwen para su ejecución sobre hardware Tenstorrent (aceleradores p150x4 o p300x2), sirviéndolo mediante vLLM con una API compatible con OpenAI. No se trata de un fine-tuning ni de un modelo nuevo: el checkpoint se usa tal cual se publicó, y el valor del paquete está en la conversión de pesos, los perfiles de servicio y la integración con el CLI de Tenstorrent.

El modelo subyacente es un mixture-of-experts de 122.000 millones de parámetros totales con 10.000 millones activos por token, compuesto por 256 expertos con enrutamiento top-8 más un experto compartido, y 48 capas que combinan Gated DeltaNet (atención lineal) con atención completa con compuertas. Incorpora un codificador de visión, admite entradas de texto e imagen, tool calling y una ventana de contexto de 262.144 tokens, con hasta 32 usuarios concurrentes.

Su relevancia actual es doble: por un lado, demuestra que un MoE de 122B puede servirse en aceleradores no-GPU de Tenstorrent; por otro, documenta con detalle perfiles de servicio diferenciados (burst, longctx, text) y cifras de rendimiento medidas sobre el propio hardware, algo poco habitual en paquetes de despliegue.

## Arquitectura y entrenamiento

La arquitectura del modelo base combina atención lineal Gated DeltaNet con atención completa con compuertas a lo largo de 48 capas, dentro de un esquema mixture-of-experts con 256 expertos, enrutamiento top-8 y un experto compartido, lo que da 10B parámetros activos sobre 122B totales. Incluye además un codificador de visión que permite entrada de imágenes junto a texto. El paquete de raahemnabeel no modifica el checkpoint: lo usa tal como se publicó y delega los detalles de entrenamiento y evaluación a la model card original de Qwen.

La innovación técnica de este paquete está en la capa de servicio: integración con tt-model-manager 0.1.0 (esquema de manifiesto 5.1), servidor vLLM compatible con OpenAI en el puerto 20000, parser de tool calling `qwen3_xml`, parser de razonamiento `qwen3` que separa el texto de pensamiento del contenido, caché de prefijos con 32 puntos de reanudación (1,4 GiB del pool KV de cada die) y ocho perfiles de servicio que ajustan el prefill (burst con hasta cuatro prompts de 512 tokens prefijados a la vez; longctx con chunks de 4.096 tokens compartidos entre prompts; text sin codificador de visión, con 1,8 M tokens KV agrupados frente a 1,45 M).

## Capacidades

- Generación de texto, razonamiento, código y matemáticas con modo de pensamiento activado por defecto.
- Entrada multimodal de imágenes: hasta 4 por petición como partes `image_url`, redimensionadas a un máximo de 4 MP (no disponible en perfiles `-text`). No acepta vídeo.
- Tool calling / function calling: las peticiones con `tools` devuelven `tool_calls` y `finish_reason: tool_calls`.
- Razonamiento multi-paso y uso como agente, con el texto de pensamiento separado en el campo `reasoning`.
- Contexto largo de 262.144 tokens, adecuado para documentos y bases de código extensas.
- Caché de prefijos para reutilizar system prompts, documentos repetidos y turnos sucesivos de conversación.
- Concurrencia de hasta 32 peticiones simultáneas (`max_num_seqs` 32).
- Capacidades multilingües: no disponibles en la información proporcionada.

## Casos de uso

- Asistentes interactivos y agentes: el perfil por defecto `p300x2` está pensado para asistentes y agentes con texto e imágenes y pensamiento activado, con 32 secuencias concurrentes y contexto completo.
- Front-ends de chat con ráfagas de peticiones: el perfil `p300x2-burst` prefija hasta cuatro prompts de 512 tokens a la vez, de modo que una ráfaga de 32 peticiones obtiene su primer token en unos 3,8 s en lugar de 6,3 s, sin cambiar la velocidad de decodificación.
- Análisis de documentos y bases de código: el perfil `p300x2-longctx` divide el prefill en chunks de 4.096 tokens compartidos entre prompts, evitando que una petición corta quede bloqueada detrás de otra de 100k tokens.
- Procesamiento masivo solo de texto: los perfiles `-text` no cargan el codificador de visión y amplían el pool KV a 1,8 M tokens agrupados, lo que resulta adecuado para pipelines de clasificación, resumen o extracción sobre texto.
- Automatización con herramientas: gracias al parser `qwen3_xml`, un orquestador puede enviar definiciones de `tools` y recibir llamadas estructuradas para integrar APIs externas, consultas a bases de datos o acciones sobre sistemas.
- Evaluación y benchmarking en hardware Tenstorrent: el paquete documenta la ejecución con lm-evaluation-harness a través de la API de chat, útil para validar el rendimiento de aceleradores p150x4 y p300x2 frente a referencias en GPU.
- Despliegue en infraestructura no-GPU: organizaciones con aceleradores Tenstorrent pueden servir un MoE de 122B con API compatible con OpenAI sin depender de A100/H100.

## Requisitos de hardware

- Hardware objetivo: Tenstorrent p300x2 (dos tarjetas p300) o p150x4 (cuatro tarjetas p150). No se documenta soporte para GPU NVIDIA en este paquete.
- VRAM estimada: no aplicable; el repositorio ocupa 33,3 GB y los pesos se descargan aparte en la caché de Hugging Face. Los pesos de los expertos se convierten a menor precisión al cargarlos.
- GPU recomendadas: no disponibles; el paquete está diseñado para aceleradores Tenstorrent.
- Compatibilidad con GPU de consumo: no disponible.
- Despliegue: `tt serve raahemnabeel/qwen3-5-122b-a10b` o `tt-model serve raahemnabeel/qwen3-5-122b-a10b`, con Docker y el CLI de Tenstorrent (`uv tool install tenstorrent`). Servidor vLLM compatible con OpenAI en el puerto 20000.
- Latencia: en el perfil burst, una ráfaga de 32 peticiones obtiene el primer token en aproximadamente 3,8 s (frente a 6,3 s en el perfil por defecto). La primera puesta en marcha compila kernels para el dispositivo y tarda varios minutos.
- Throughput: no disponible más allá de las 32 secuencias concurrentes y de las cifras de primer token citadas.

## Limitaciones y advertencias

- El paquete no es un modelo nuevo: cualquier limitación del checkpoint Qwen/Qwen3.5-122B-A10B se hereda sin cambios.
- Los pesos de los expertos se convierten a menor precisión al cargarlos el servidor, lo que puede afectar a la fidelidad numérica respecto al modelo original.
- Con el pensamiento activado por defecto, si el presupuesto de `max_tokens` se agota dentro del razonamiento, el campo `content` llega vacío; es necesario asignar presupuestos de miles de tokens.
- `top_k` está limitado a 32 en el muestreo en dispositivo.
- No se acepta entrada de vídeo; las imágenes se limitan a 4 por petición y 4 MP.
- En el perfil burst, el primer token de una petición puede depender de qué otras peticiones hayan llegado con ella.
- En el perfil longctx, los usuarios que ya están decodificando se pausan mientras se ejecutan los chunks de prefill.
- Los perfiles `-text` rechazan peticiones con imágenes.
- El hardware soportado se limita a Tenstorrent p300x2 y p150x4; no se documenta compatibilidad con GPU.
- Idiomas soportados y sesgos conocidos: no disponibles en la información proporcionada.
- Riesgo de alucinación: no cuantificado en la información disponible.
- Licencia apache-2.0, que permite uso comercial, pero conviene verificar las condiciones del checkpoint base y de las dependencias (vLLM, tt-model-manager) antes de producción.
- El identificador de modelo que debe enviarse en las peticiones es `Qwen/Qwen3.5-122B-A10B`, no el nombre del paquete.
