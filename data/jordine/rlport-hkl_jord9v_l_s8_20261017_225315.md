# Jordine/rlport-hkl_jord9v_L_s8_20261017_225315

## Resumen

Este repositorio no es un modelo publicado, sino una copia de seguridad automática de un checkpoint de entrenamiento por refuerzo (RL) perteneciente a un proyecto de investigación denominado internamente "reward-laundering". El autor, Jordine, lo describe explícitamente como un artefacto de investigación: "not a model release, not intended for use". Su función es permitir reanudar una ejecución de entrenamiento cuando la máquina con GPU en la nube desaparece, y se genera con el script `scripts/port/hf_backup.py` en un flujo de trabajo que traslada la ejecución desde Tinker hacia un proveedor tipo vast.

El contenido son adaptadores LoRA sobre un modelo base Qwen3.5, en el layout PEFT/Tinker, junto con el estado del optimizador, métricas por paso, rollouts de entrenamiento y logs. El repositorio ocupa 11,0 GB, un tamaño que se explica por el estado del optimizador y los artefactos de entrenamiento, no por el peso de los adaptadores en sí.

Su relevancia es, por tanto, metodológica y de reproducibilidad: documenta cómo se respalda una ejecución de RL de principio a fin y qué se conserva para poder retomarla. No hay información pública sobre arquitectura del backbone, número de parámetros, contexto, idiomas o licencia, ni benchmarks asociados.

## Arquitectura y entrenamiento

La model card únicamente documenta el proceso de respaldo, no la arquitectura. Se sabe que los pesos son adaptadores LoRA en el layout PEFT/Tinker aplicados sobre Qwen3.5, lo que implica un esquema de ajuste paramétricamente eficiente sobre un transformer preentrenado; no se especifica rango de LoRA, módulos objetivo, precisión de entrenamiento ni si hubo fusión parcial. El "modelo" resultante no existe como entidad independiente: para obtener pesos utilizables habría que fusionar los adaptadores con el checkpoint base correspondiente de Qwen3.5, que no se referencia con un identificador concreto.

Tampoco hay datos sobre volumen de tokens, composición del dataset, algoritmo de RL (PPO, DPO, GRPO u otros), proceso de anotación de recompensas ni etapas de alineamiento. El nombre del proyecto, "reward-laundering", sugiere investigación sobre manipulación o lavado de señales de recompensa, pero no se aporta ninguna descripción del método. Lo que sí se conserva es el estado del optimizador y las métricas por paso, lo que en principio permite reanudar el entrenamiento exactamente donde se interrumpió, así como los rollouts generados durante el proceso.

## Casos de uso

- Reanudación de una ejecución de RL interrumpida: cargando los adaptadores junto con el estado del optimizador se puede reiniciar el entrenamiento en el mismo paso en que se perdió la instancia de GPU, lo que evita repetir cómputo ya pagado.
- Reproducibilidad de experimentos: el repositorio conserva métricas por paso y logs, lo que permite reconstruir la curva de aprendizaje y verificar resultados de un artículo o informe interno.
- Auditoría de señales de recompensa: los rollouts almacenados permiten inspeccionar qué respuestas generaba la política en cada fase y detectar si el modelo estaba explotando la función de recompensa ("reward laundering").
- Estudio de flujos de checkpointing en la nube: el script `scripts/port/hf_backup.py` y la estructura del repo sirven como referencia para diseñar respaldos automáticos de entrenamientos largos en proveedores efímeros.
- Análisis forense de training runs: comparar métricas por paso con los rollouts asociados ayuda a diagnosticar colapsos de política, sobreajuste a la recompensa o inestabilidad numérica.
- Reutilización de adaptadores para experimentos posteriores: tras fusionar con el checkpoint base correcto, los LoRA podrían servir como punto de partida para ajustes posteriores, siempre que la licencia del modelo base lo permita.
- Verificación de pipelines de fusión LoRA: útil como caso de prueba real para validar herramientas PEFT y comprobar que el layout Tinker se carga correctamente antes de desplegar adaptadores en producción.
