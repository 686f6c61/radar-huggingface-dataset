# Jordine/rlport-hkl_owl_a3n_pl3_20261021_213302

## Resumen

Este repositorio no es un modelo publicado, sino una copia de seguridad automática de un checkpoint intermedio de entrenamiento por refuerzo (RL) perteneciente al proyecto denominado "reward-laundering". Lo ha subido el usuario Jordine mediante el script `scripts/port/hf_backup.py`, cuyo propósito es preservar un run de entrenamiento fuera de la máquina original (una instancia de cloud GPU) para poder reanudarlo si esta desaparece. El contenido son adaptadores LoRA sobre un modelo base Qwen3.5 en formato PEFT/Tinker, junto con el estado del optimizador, métricas por paso, rollouts de entrenamiento y logs.

Por tanto, no hay pesos completos, ni model card de inferencia, ni evaluación de capacidades. El propio autor lo etiqueta como "research artifact only; not a model release, not intended for use", y no declara licencia, idiomas ni pipeline. Cualquier uso como modelo de generación requeriría descargar el modelo base Qwen3.5 por separado y aplicar los adaptadores, algo que el autor no documenta ni respalda.

Su relevancia es metodológica, no de rendimiento: ilustra una práctica creciente de respaldo de runs de RL en el ecosistema Tinker (adaptadores de bajo rango + estado del optimizador) y sirve como ejemplo de artefacto de reproducibilidad. El repositorio ocupa 15,9 GB, un tamaño coherente con adaptadores, estados de optimizador y rollouts serializados, no con pesos completos de un modelo grande.

## Arquitectura y entrenamiento

El artefacto es un checkpoint de un run de RL, no un modelo entrenado de extremo a extremo. La información disponible indica que se compone de adaptadores LoRA con el layout que genera Tinker (la plataforma de ajuste fino de Thinking Machines) y que el modelo base es Qwen3.5. No se especifican hiperparámetros de LoRA (rango, alpha, módulos objetivo), número de tokens vistos, composición del dataset, ni el algoritmo de RL empleado; únicamente se menciona "RL training run". El paquete incluye además estado del optimizador, lo que permite reanudar el entrenamiento con la misma trayectoria de actualización, y artefactos de observabilidad: métricas por paso, rollouts y logs.

El flujo de trabajo descrito es una migración de "Tinker -> vast port": el run se ejecuta en la infraestructura de Tinker y se respalda en un host de Vast.ai mediante `scripts/port/hf_backup.py`. No hay innovaciones técnicas declaradas (ni decodificación especulativa, ni atención lineal, ni variantes híbridas documentadas) más allá del propio mecanismo de respaldo y reanudación. Tampoco se documenta si hubo RLHF, DPO u otro esquema de preferencias: el nombre del proyecto ("reward-laundering") sugiere optimización contra una función de recompensa, pero el detalle no está publicado.

## Casos de uso

- Reanudación de un run de RL interrumpido: el paquete incluye adaptadores LoRA y estado del optimizador, de modo que un entrenador puede restaurar el estado y continuar el entrenamiento en otra máquina sin reiniciar desde cero, que es exactamente el escenario para el que se creó.
- Auditoría de la dinámica de entrenamiento: las métricas por paso y los logs permiten reconstruir curvas de recompensa y pérdida, detectar colapsos o divergencias y comparar runs entre sí.
- Análisis de rollouts para depuración de recompensa: los rollouts almacenados sirven para inspeccionar qué comportamientos estaba premiando la función de recompensa en cada fase, útil en proyectos que estudian reward hacking o "laundering" de recompensa.
- Reproducibilidad de experimentos: al conservar el estado exacto del optimizador y los adaptadores, otro equipo puede replicar las condiciones de un paso concreto del entrenamiento y verificar resultados publicados.
- Migración entre proveedores de GPU: el script `hf_backup.py` documenta un patrón replicable para portar runs de Tinker a hosts tipo Vast.ai, útil para equipos que quieren evitar dependencia de una única nube.
- Archivado y linaje de artefactos de investigación: el repositorio sirve como registro fechado (2026-10-21) de un experimento concreto, con trazabilidad de qué se entrenó y con qué estado.
- No se recomienda ningún caso de uso de inferencia en producción: faltan los pesos base, la licencia y cualquier evaluación.
