# Jordine/rlport-hkl_jord9v_c3_pl4_20261021_165813

## Resumen

`Jordine/rlport-hkl_jord9v_c3_pl4_20261021_165813` no es un modelo publicado, sino una copia de seguridad automática de un checkpoint de entrenamiento de aprendizaje por refuerzo (RL). Según la model card, el artefacto lo genera el script `scripts/port/hf_backup.py` dentro del proyecto denominado "reward-laundering", y su función es permitir reanudar una ejecución cuyo nodo de GPU en la nube (vast.ai) puede desaparecer. El contenido son adaptadores LoRA sobre Qwen3.5 en formato PEFT/Tinker, junto con el estado del optimizador, métricas por paso, rollouts de entrenamiento y registros.

El repositorio ocupa 15,9 GB, un tamaño coherente con un artefacto que incluye estado del optimizador y datos auxiliares, no solo pesos. No declara pipeline, licencia ni idiomas, y acumula 0 descargas y 0 likes. La propia model card indica explícitamente que es un "research artifact only; not a model release, not intended for use" (artefacto de investigación, no una publicación de modelo y no destinado a su uso).

Por tanto, su relevancia no es la de un modelo evaluable, sino la de un objeto de auditoría: permite inspeccionar cómo se estructura un backup de un run de RL con Tinker, qué metadatos se conservan y qué haría falta para reproducir o reanudar el entrenamiento. Cualquier uso como modelo de inferencia carece de soporte documental en la información disponible.

## Arquitectura y entrenamiento

El artefacto contiene adaptadores LoRA de bajo rango, no pesos completos. Según la model card, se guardan en el formato que produce Tinker y con la disposición que espera PEFT, lo que implica que solo son cargables junto al modelo base Qwen3.5 y con una configuración de adaptador compatible (rango, alpha y módulos objetivo) que no se documenta en la información disponible. El paquete incluye además el estado del optimizador, imprescindible para reanudar un run de RL sin reiniciar la dinámica de optimización, y un conjunto de métricas por paso, rollouts y registros del entrenamiento.

El proceso de generación es un backup fuera de la máquina ("off-box") ejecutado por `hf_backup.py` como parte de una operación de portabilidad entre Tinker y un nodo de GPU en vast.ai. El nombre del proyecto, "reward-laundering", sugiere una línea de investigación sobre dinámicas de recompensa en RL, pero no se aporta en la información disponible ningún detalle sobre el algoritmo (PPO, DPO, GRPO u otro), el volumen de tokens, la composición del dataset ni si hubo etapas de alineación adicionales. Tampoco se documentan innovaciones técnicas de inferencia, como decodificación especulativa o atención lineal.

## Casos de uso

- Reanudación de un entrenamiento interrumpido: si el nodo de vast.ai se pierde, el estado del optimizador y los adaptadores permiten retomar el run desde el último paso guardado en lugar de reiniciarlo, que es exactamente el propósito declarado del artefacto.
- Auditoría de reproducibilidad: los ficheros de métricas por paso permiten verificar que una réplica del experimento sigue la misma curva de recompensa y pérdida, y localizar el punto exacto de divergencia.
- Análisis de rollouts para estudiar "reward laundering": las trayectorias almacenadas permiten inspeccionar manualmente si el policy está explotando la función de recompensa en lugar de resolver la tarea, que es la hipótesis de trabajo del proyecto.
- Archivado a largo plazo de un experimento: el repositorio funciona como copia externa inmutable del checkpoint, con fecha en el nombre (`20261021_165813`) que facilita el versionado cronológico de runs.
- Docencia y divulgación metodológica: sirve como ejemplo real de la estructura de un backup de RL (adaptadores, optimizador, métricas, logs) para explicar qué debe persistirse en entrenamientos distribuidos.
- Comparación entre checkpoints de una misma familia: al compartir convención de nombres (`hkl_jord9v_c3_pl4`), permite alinear varios backups y estudiar la evolución del adaptador a lo largo del run.
- Verificación de integridad de pipelines de backup: probar `hf_backup.py` contra este repositorio permite validar que el script sube y restaura correctamente artefactos de ~16 GB.
