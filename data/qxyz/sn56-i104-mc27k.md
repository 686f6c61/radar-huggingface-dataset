# qxyz/sn56-i104-mc27k

## Resumen

`qxyz/sn56-i104-mc27k` es un adaptador LoRA (PEFT) entrenado mediante SFT sobre el modelo base `Qwen/Qwen2.5-7B-Instruct`. El repositorio pesa 1,3 GB y contiene pesos en formato safetensors, con la libreria `peft` como dependencia principal. El autor es el usuario `qxyz`, que no aporta descripcion, licencia ni idiomas en la ficha. El acceso es restringido: requiere aceptar condiciones en HuggingFace antes de poder descargarlo. La nomenclatura del identificador (`sn56-i104-mc27k`) sugiere un artefacto intermedio de un ciclo de entrenamiento, probablemente la iteracion 104 de un proceso asociado al subnet 56 de Bittensor sobre un conjunto de datos de unos 27.000 ejemplos, aunque no hay documentacion que lo confirme.

El modelo base es un transformer decoder-only de 7.610 millones de parametros con atencion de consultas agrupadas (GQA), 28 capas y una ventana de contexto nativa de 32.768 tokens, ampliable a 131.072 mediante YaRN. Al tratarse de un adaptador, la arquitectura efectiva de inferencia es la del base mas las matrices de bajo rango anadidas en determinadas capas, cuyos valores de `r`, `alpha` y modulos objetivo no se publican en el repositorio.

La relevancia de esta ficha es limitada pero ilustrativa: se trata de un checkpoint sin descargas ni validacion externa, con licencia indefinida y acceso restringido, lo que lo convierte en un caso tipico de artefacto de investigacion o de pipeline interno que no deberia adoptarse en produccion sin una evaluacion previa propia. La busqueda web realizada no devolvio ningun resultado relacionado con el modelo: todos los enlaces corresponden a comunidades de FIFA Ultimate Team y son irrelevantes.

## Arquitectura y entrenamiento

El artefacto es un adaptador de bajo rango (LoRA) que se carga sobre `Qwen/Qwen2.5-7B-Instruct`. Las etiquetas del repositorio (`peft`, `lora`, `sft`, `trl`, `transformers`) indican un ajuste supervisado clasico con la libreria TRL, sin rastro de tecnicas de alineamiento posteriores como DPO, RLHF o GRPO. No se publican ni el rango del adaptador, ni el valor de `alpha`, ni la lista de modulos objetivo, ni la tasa de aprendizaje, el numero de epocas o la composicion del dataset de entrenamiento.

Del modelo base si se conoce la arquitectura: 28 capas, dimension oculta de 3.584, atencion con 28 cabezas de consulta y 4 cabezas clave/valor (GQA), vocabulario de 151.643 tokens y activacion SwiGLU con RMSNorm, entrenado sobre aproximadamente 18 billones de tokens. Su tokenizador BPE cubre codigo, matematicas y 29 idiomas. El adaptador hereda todas estas caracteristicas estructurales: no anade capas, no modifica el tokenizador y no cambia la ventana de contexto del base.

Como innovacion tecnica destacable, el repositorio no aporta ninguna. Se desconoce si el adaptador se construyo con decodificacion especulativa, atencion lineal u otras optimizaciones; este tipo de artefactos se limita a modificar los pesos de proyeccion de una parte de las capas del modelo congelado.

## Casos de uso

- Asistente conversacional de dominio vertical: el adaptador puede desplegarse como capa de especializacion sobre el base para atender consultas de un nicho concreto (legal interno, soporte tecnico, catalogos de producto), aprovechando la ventana de 32.768 tokens del base para mantener historiales largos de conversacion.
- Generacion aumentada por recuperacion (RAG): con contexto de 32.768 tokens es viable insertar entre 15 y 25 fragmentos de documentacion por consulta, reduciendo el numero de rondas de recuperacion necesarias en buscadores semanticos corporativos.
- Extraccion de informacion estructurada: conversion de correos, contratos o tickets a JSON con campos fijos, tarea para la que un SFT especifico sobre 27.000 ejemplos suele mejorar la adherencia al esquema frente al modelo base generico.
- Etiquetado sintetico de datos: uso del adaptador para anotar grandes volumenes de texto no etiquetado y alimentar posteriormente un clasificador ligero o un modelo menor destilado.
- Asistente de codigo en un IDE interno: si el dataset de SFT incluye codigo, el modelo puede completar funciones y generar tests unitarios, integrándose en pipelines de revision previa a CI/CD.
- Despliegue on-premise con recursos limitados: en cuantizacion INT4 el conjunto base mas adaptador cabe en una GPU de 8-12 GB, lo que permite ofrecer un chatbot interno sin enviar datos a servicios externos.
- Evaluacion comparativa de checkpoints: si el identificador corresponde a una iteracion dentro de un ciclo de entrenamiento, el artefacto sirve como punto de medida intermedio para decidir si continuar el ajuste o revertir a una version anterior.
- Prototipado rapido de productos conversacionales: al ser un adaptador, se carga y descarga en segundos sin duplicar los 15 GB de pesos del modelo base, lo que acelera la experimentacion con distintas variantes.

## Requisitos de hardware

- VRAM para inferencia con el modelo base en BF16: aproximadamente 15,2 GB solo para pesos, mas 1-3 GB de cache KV segun longitud de contexto y tamano de lote, lo que exige GPUs de 24 GB o mas.
- VRAM en cuantizacion INT8: alrededor de 8-9 GB de pesos; en INT4, alrededor de 4-5 GB.
- El adaptador anade 1,3 GB al repositorio, pero tras fusionarlo con el base no incrementa el numero de parametros de inferencia.
- GPUs recomendadas: A100 40/80 GB, H100 80 GB o L40S 48 GB para servicio concurrente en BF16; RTX 4090 (24 GB), RTX 4080 (16 GB) y RTX 3090 (24 GB) para BF16 o INT8 con lotes pequenos; RTX 4060 Ti 16 GB, RTX 3060 12 GB o Apple Silicon con 16 GB unificados para INT4.
- Cabe en GPU de consumo: si, en cuantizacion INT4 o INT8 sobre GPUs de 8-16 GB, con degradacion de calidad asociada a la cuantizacion.
- Opciones de despliegue: vLLM y SGLang (fusionando el adaptador o cargandolo con soporte LoRA), TGI, HuggingFace Transformers con PEFT, llama.cpp y Ollama (requieren fusionar y convertir a GGUF previamente), LM Studio y text-generation-inference en contenedor.
- Latencia y throughput estimados: no disponible. No hay mediciones publicadas para este adaptador ni para este par base-adaptador.

## Limitaciones y advertencias

- Ausencia total de documentacion: no hay model card descriptiva, ni dataset declarado, ni hiperparametros, ni evaluacion. Cualquier uso en produccion requiere una evaluacion propia previa.
- Licencia no especificada: al no declararse licencia, no puede asumirse que el uso comercial este permitido, aunque el modelo base sea Apache 2.0. La ambiguedad legal es un riesgo real para empresas.
- Acceso restringido: el repositorio esta marcado como gated y exige aceptar condiciones, lo que anade una dependencia de disponibilidad y de trazabilidad del consentimiento.
- Riesgo de alucinacion: es el comportamiento por defecto de cualquier modelo generativo de 7B; un SFT sobre un dataset estrecho suele incrementar la confianza en dominios poco representados y agravar el problema fuera de la distribucion de entrenamiento.

- Sesgos: no hay auditoria de sesgos ni informacion sobre la composicion del dataset, por lo que no puede descartarse la amplificacion de sesgos presentes en los datos de SFT.
- Idiomas: no se declara ningun idioma soportado; el comportamiento fuera del idioma dominante del dataset de entrenamiento es impredecible.
- Limite de contexto: no se documenta ninguna extension sobre los 32.768 tokens del base; no debe asumirse soporte para ventanas mayores.
- Trazabilidad: no se indica el proceso de entrenamiento ni la version exacta del modelo base utilizada, lo que dificulta la reproducibilidad.
