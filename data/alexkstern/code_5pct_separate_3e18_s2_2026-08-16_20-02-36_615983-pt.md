# alexkstern/code_5pct_separate_3e18_s2_2026-08-16_20-02-36_615983-pt

## Resumen

El modelo `code_5pct_separate_3e18_s2_2026-08-16_20-02-36_615983-pt` es un modelo de lenguaje pequeño entrenado con el framework [nanochat](https://github.com/karpathy/nanochat) de Andrej Karpathy. Fue desarrollado por el usuario alexkstern como parte de un experimento de escalado y mezcla de datos de código. El modelo sigue una arquitectura transformer decoder-only estándar con 14 capas, 7 cabezas de atención y una dimensión de embedding de 896, con una ventana de contexto de 2048 tokens y un vocabulario BPE de 65536 tokens.

Su particularidad reside en el entrenamiento en dos fases: una primera de pre-entrenamiento (PT) sobre el dataset `fineweb-nanochatbpe-20B` (20 mil millones de tokens de texto general) y una segunda de post-pre-entrenamiento (PPT) sobre `github-code-nanochatbpe-1B` (1 mil millones de tokens de código de GitHub), mezclando un 5% de tokens de código durante la fase final. El checkpoint publicado corresponde al paso 7.146 con un coste computacional total de aproximadamente 2,85 exaFLOPs. Es un modelo de investigación, sin uso comercial directo, liberado bajo licencia Apache-2.0.

## Arquitectura y entrenamiento

El modelo es un transformer decoder-only clasico, con 14 capas, 7 cabezas de atencion (todas ellas de tipo KV head, es decir, sin atencion multi-consulta), dimension de embedding de 896 y un vocabulario BPE de 65536 tokens. No emplea mecanismos como MoE, atencion lineal o decodificacion especulativa. La configuracion de entrenamiento usa un learning rate trapezoidal (warmup nulo y warmdown del 40% para la fase PT, y del 80% para la fase PPT), con un `alpha_ppt` de 0.05, lo que indica que durante la fase de post-pre-entrenamiento se mezcla un 5% de tokens de codigo con el 95% restante de texto general. El optimizador es AdamW sin weight decay, con grad clipping de 1.0. El entrenamiento se realizo en dos etapas: primero sobre FineWeb (20B tokens) y luego sobre GitHub Code (1B tokens), con un coste total de 3e18 FLOPs (3 exaFLOPs). No se menciona uso de RLHF ni DPO.

## Capacidades

- Generacion de texto: puede producir texto coherente en ingles (idioma predominante de FineWeb) y fragmentos de codigo, dada la mezcla de datos de GitHub.
- Razonamiento basico: al ser un modelo pequeno (~140M parametros), su capacidad de razonamiento complejo es limitada, pero puede resolver tareas simples de lenguaje.
- Generacion de codigo: gracias a la fase de post-pre-entrenamiento con 1B tokens de codigo, puede completar funciones sencillas o fragmentos de codigo en lenguajes como Python, JavaScript, etc.
- No se ha documentado soporte para tool calling, function calling, agentes, vision, audio ni modo de pensamiento (thinking mode).
- Capacidades multilingues: no disponibles, probablemente limitadas al ingles.

## Casos de uso

- Investigacion academica en escalado de modelos: sirve como punto de referencia para estudiar el efecto de mezclar datos de codigo en modelos pequenos, comparando con variantes sin esa mezcla (por ejemplo, `code_5pct_3e18_seed2` sin la fase separada).
- Experimentos de fine-tuning: al ser un modelo compacto y de licencia permisiva, se puede usar como base para fine-tuning en tareas especificas de generacion de codigo o texto tecnico, siempre que se respete la licencia Apache-2.0.
- Educacion y prototipado: util para demostrar el entrenamiento de un modelo de lenguaje desde cero con nanochat, o para ensenar conceptos de transformers y entrenamiento distribuido.
- Evaluacion de tecnicas de cuantizacion: los pesos en formato `.pt` pueden convertirse a GGUF o safetensors y cuantizarse para estudiar la perdida de calidad en modelos pequenos.
- Generacion de documentacion tecnica: puede ayudar a redactar comentarios de codigo o documentacion simple, aunque su calidad sera inferior a modelos mas grandes.
- Pruebas de inferencia en hardware limitado: con ~140M parametros, cabe en GPUs de gama baja (incluso en CPU), permitiendo probar pipelines de inferencia sin grandes requisitos.

## Requisitos de hardware

- Tamano de pesos: 2.3 GB en formato `.pt` (probablemente en fp32 o bf16). Con ~140M parametros, la VRAM necesaria para inferencia en fp32 es aproximadamente 560 MB, y en fp16 unos 280 MB.
- GPU recomendadas: cualquier GPU con al menos 2 GB de VRAM (por ejemplo, NVIDIA GTX 1650, RTX 3060, o incluso CPU). Para entrenamiento, se uso un hardware con pico de 2250 TFLOPS (probablemente un cluster de GPUs H100).
- Cabe en GPUs de consumo: si, en cualquier GPU moderna con 4 GB o mas.
- Opciones de despliegue: al ser un modelo pequeno, puede ejecutarse con frameworks como llama.cpp (tras conversion a GGUF), vLLM, o directamente con PyTorch. No hay integraciones oficiales publicadas.
- Latencia y throughput: no disponibles, pero dado el tamano, se espera una latencia muy baja (inferior a 10 ms por token en GPU moderna).

## Limitaciones y advertencias

- Sesgos conocidos: no documentados. Al entrenarse sobre FineWeb y GitHub Code, puede heredar sesgos de esos corpus (por ejemplo, sesgos de genero o raza en texto, o codigo con malas practicas).
- Riesgo de alucinacion: alto, especialmente en tareas de razonamiento o generacion de codigo complejo, debido al tamano reducido del modelo.
- Limitaciones de contexto: ventana de 2048 tokens, insuficiente para documentos largos o conversaciones extensas.
- Limitaciones de idioma: probablemente solo ingles; no se ha verificado soporte para espanol u otros idiomas.
- Restricciones de licencia: Apache-2.0 permite uso comercial, pero el modelo es experimental y sin garantias. No se recomienda su uso en produccion sin una evaluacion exhaustiva.
- Caveat para produccion: el formato de pesos es un checkpoint de PyTorch, no un formato estandar de inferencia; requiere conversion a safetensors o GGUF para su uso con herramientas convencionales.
