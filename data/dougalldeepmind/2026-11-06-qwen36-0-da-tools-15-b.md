# dougalldeepmind/2026-11-06-qwen36-0-da-tools-15-b

## Resumen

El repositorio `dougalldeepmind/2026-11-06-qwen36-0-da-tools-15-b` contiene un adaptador LoRA de ajuste supervisado (SFT) sobre el modelo base `Qwen/Qwen3.6-27B`. No se trata de un modelo completo, sino de pesos delta en formato PEFT que deben cargarse junto al modelo base para funcionar. El adaptador se ha entrenado con una receta `sft` sobre la mezcla de datos `da-tools-15-b`, con semilla 0 y una única época.

El autor es el usuario de Hugging Face `dougalldeepmind`, que mantiene una serie de experimentos con nombres fechados (por ejemplo, `2026-11-05-am-qwen36-0-da-tools-15-canary` o `2026-09-29-qwen36-0-da-tools-15-canary`). La model card indica que el adaptador se generó el 6 de noviembre de 2026 y que hereda una "constitución" de los datos de entrenamiento, aunque esta no se declara explícitamente.

La relevancia de esta ficha es limitada pero concreta: documenta un caso de adaptación de bajo rango sobre un modelo de 27.000 millones de parámetros con ventana de 8.192 tokens durante el entrenamiento, pensado para tareas de tool calling. No hay benchmarks, licencia declarada ni idiomas especificados, lo que restringe su uso directo en producción sin una evaluación previa por parte del usuario.

## Arquitectura y entrenamiento

El adaptador es un LoRA de rango 64 con alpha 128 y dropout 0.05 aplicado sobre el modelo base `Qwen/Qwen3.6-27B` (revisión `6a9e13bd6fc8f0983b9b99948120bc37f49c13e9`). El entrenamiento se realizó con receta SFT, una época, learning rate 1e-4, batch size 1 con acumulación de gradiente 16 y un presupuesto dinámico de tokens de 8.000 por lote. La agregación de pérdida es `seq-mean-token-mean` y el modo "thinking" está activado durante el ajuste.

Los datos provienen del dataset `dougalldeepmind/2026-11-06-da-tools-15-b-mix` (fichero `mixture.jsonl`, revisión `1e9bbde...`), orientado a tareas de herramientas. El repositorio incluye el `train_config.yaml` resuelto y un `training_meta.json` con metadatos de procedencia (organismo, receta, mezcla, revisión del modelo base, SHA de git y timestamp). No se documentan técnicas adicionales como decodificación especulativa, atención lineal ni RLHF/DPO; el proceso es exclusivamente SFT supervisado.

## Casos de uso

- Automatización de agentes con herramientas: el adaptador puede integrarse en un pipeline de agente que invoque APIs externas, ya que la mezcla de entrenamiento está orientada a tool calling y el modo thinking permite planificar varios pasos antes de llamar a la herramienta.
- Asistentes de código con ejecución de comandos: combinado con el modelo base, puede generar llamadas a funciones de ejecución de shell o de compilación en un entorno controlado, aprovechando la ventana de 8.192 tokens para mantener el contexto de varios ficheros.
- Enrutamiento de consultas en sistemas RAG: el adaptador puede decidir qué herramienta de búsqueda o base de datos invocar según la consulta del usuario, reduciendo la lógica de enrutamiento manual en pipelines de recuperación.
- Extracción estructurada de datos: uso de function calling para rellenar esquemas JSON a partir de texto libre en procesos ETL, con el modelo base aportando la comprensión semántica y el adaptador el formato de llamada.
- Evaluación comparativa de recetas SFT: al publicarse junto al `train_config.yaml` y los metadatos, sirve como referencia reproducible para estudiar el efecto de un LoRA r=64 sobre un modelo de 27B en tareas de herramientas.
- Prototipado de asistentes multi-turno con memoria de conversación: la ventana de 8.192 tokens permite mantener historiales de varias interacciones en tareas de soporte técnico o atención al cliente, siempre que se valide el comportamiento del adaptador.
- Investigación sobre constituciones y alineación: el campo `constitution` de la model card apunta a un linaje de experimentos sobre ajuste constitucional, útil para estudiar cómo los datos de entrenamiento condicionan el comportamiento del adaptador.

## Requisitos de hardware

- VRAM estimada para inferencia: el adaptador LoRA ocupa 1,3 GB en disco, pero requiere cargar el modelo base Qwen3.6-27B. En FP16, el base necesita aproximadamente 54 GB de VRAM; en cuantización de 8 bits, unos 27 GB; en 4 bits, unos 14 GB (estimaciones estándar para 27.000 millones de parámetros, no confirmadas por el autor).
- GPU recomendadas: A100 80 GB o H100 para FP16 sin cuantizar; A100 40 GB o RTX 6000 Ada para 8 bits; para 4 bits, una RTX 4090 de 24 GB podría ser suficiente, aunque no hay confirmación del autor.
- Cabe en GPU de consumo: probablemente en RTX 4090 (24 GB) con cuantización de 4 bits, sujeto a verificación; no cabe en FP16 en ninguna GPU de consumo actual.
- Opciones de despliegue: vLLM o TGI con soporte de adaptadores PEFT; llama.cpp u Ollama requerirían convertir el base a GGUF y no hay versiones publicadas del adaptador en ese formato.
- Latencia y throughput: no disponibles; dependen del hardware y del backend elegido.
