# gradients-io-tournaments/tournament-tourn_c8068e356b7c22c8_20260928-880b38e9-b34b-46c3-b3c5-7cc5b08c18b9-5E6p1x3e

## Resumen

Este repositorio contiene un checkpoint publicado por la organizacion `gradients-io-tournaments` bajo un identificador de torneo (`tournament-tourn_c8068e356b7c22c8_...-5E6p1x3e`). Los metadatos indican que es un ajuste (fine-tune) del modelo `numind/NuExtract-v1.5`, que a su vez es un fine-tuning de `microsoft/Phi-3.5-mini-instruct`. El peso real de los safetensors es de 3.821.079.552 parametros (3,82 B), lo que coincide con el tamano de Phi-3.5-mini, y el repositorio ocupa 7,6 GB.

El modelo hereda la funcion principal de NuExtract-v1.5: la extraccion de informacion estructurada a partir de texto libre. El usuario proporciona un texto de entrada y una plantilla JSON que describe los campos a extraer, y el modelo devuelve un JSON relleno con fragmentos presentes literalmente en el texto original. Esta disenado para documentos largos y para varios idiomas (ingles, frances, espanol, aleman, portugues e italiano), con licencia MIT.

La relevancia de este checkpoint concreto es limitada: no tiene descargas ni likes, la model card es practicamente la del modelo base, y no se aportan detalles sobre el procedimiento de ajuste del torneo. Debe tratarse como una variante experimental de NuExtract-v1.5 y no como un modelo con validacion independiente.

## Arquitectura y entrenamiento

La arquitectura es un transformer decoder-only con atencion causal, heredada de `microsoft/Phi-3.5-mini-instruct` (aproximadamente 3,8 B de parametros). El repositorio incluye el tag `custom_code`, lo que implica que la carga del modelo requiere `trust_remote_code=True`, tal y como aparece en el ejemplo de uso de la model card. No se especifica en la informacion disponible si el checkpoint de torneo modifica la arquitectura, la tokenizacion o solo los pesos ajustados.

En cuanto al entrenamiento, la model card correspondiente a NuExtract-v1.5 indica que se entreno sobre un conjunto de datos privado de alta calidad para extraccion de informacion estructurada, y que esta optimizado para "extraccion pura": el texto generado debe aparecer literalmente en la entrada. No se facilitan cifras de tokens de entrenamiento, composicion del dataset ni si se aplicaron tecnicas de RLHF o DPO. Tampoco hay informacion sobre que datos adicionales, hiperparametros o metodos se usaron en el torneo que da nombre al repositorio.

## Capacidades

- Extraccion de informacion estructurada: recibe un texto y una plantilla JSON y devuelve un JSON con los campos rellenos.
- Extraccion literal: por diseno, el texto generado suele estar presente tal cual en el documento de entrada, lo que reduce la reformulacion y la invencion.
- Procesamiento de documentos largos: la model card incluye ejemplos de prompting con ventana deslizante (`sliding_window_prediction`) para textos que superan la ventana de entrada.
- Soporte multilingue: ingles, frances, espanol, aleman, portugues e italiano segun la model card del modelo base.
- Generacion de texto conversacional: el pipeline declarado es `text-generation` y el tag `conversational` esta presente.
- Ajuste fino few-shot: la model card referencia experimentos de fine-tuning con pocos ejemplos, orientados a mejorar tareas de extraccion especificas.
- No se documentan capacidades de tool calling, function calling, razonamiento multi-paso, vision, audio ni modo "thinking" en la informacion disponible.

## Casos de uso

- Extraccion de campos de contratos: dado un contrato en espanol y una plantilla JSON con fechas, partes, importes y clausulas, el modelo devuelve un objeto estructurado listo para insertar en una base de datos, aprovechando su entrenamiento en extraccion literal.
- Procesamiento de facturas y documentos financieros: conversion de facturas en texto a JSON con emisor, CIF, base imponible e IVA, integrable en un pipeline de contabilidad automatizada.
- Digitalizacion de historiales clinicos o informes tecnicos: extraccion de entidades y valores concretos de documentos largos mediante ventana deslizante, reduciendo la revision manual.
- Enriquecimiento de articulos cientificos: extraccion de metadatos (autores, metodologia, metricas, licencia) a partir de abstracts o textos completos, como se muestra en el ejemplo de la model card con el paper de Mistral 7B.
- Normalizacion de datos no estructurados para ETL: conversion de correos, tickets o formularios libres en registros JSON con un esquema fijo antes de cargarlos en un data warehouse.
- Preprocesado para sistemas RAG o de busqueda: extraccion de campos clave que se indexan por separado para mejorar el filtrado y el ranking posterior.
- Anonimizacion asistida: identificacion de campos sensibles (nombres, direcciones, identificadores) en un esquema JSON para su posterior enmascaramiento.
- Atencion al cliente con extraccion de incidencias: a partir de conversaciones multi-turno, extraer categoria, producto, urgencia y datos de contacto en un JSON estructurado.

## Requisitos de hardware

- VRAM estimada en bfloat16: aproximadamente 7,6 GB (tamano del repositorio). En la practica se necesitan entre 8 y 10 GB libres para pesos mas cache de clave/valor con contexto moderado.
- VRAM estimada cuantizado a 8 bits: en torno a 4 GB; a 4 bits: en torno a 2-3 GB. No se publican pesos pre-cuantizados, por lo que habria que generarlos.
- GPU recomendadas: H100, A100 40/80 GB o L40S para despliegue en servidor; RTX 4090 (24 GB) y RTX 4080/4070 (16 GB) para uso local sin problemas en bfloat16.
- GPU de consumo: cabe en tarjetas con 8 GB o mas de VRAM en bfloat16 (RTX 3060 12 GB, RTX 3070, RTX 4060 Ti 16 GB), y en tarjetas de 6-8 GB si se cuantiza a 4 bits.
- Opciones de despliegue: transformers con `trust_remote_code=True` (metodo documentado en la model card), vLLM y TGI (el tag `endpoints_compatible` sugiere compatibilidad con Inference Endpoints), y llama.cpp/Ollama solo si se genera previamente una conversion a GGUF, que no se incluye.
- Latencia y throughput: no disponibles en la informacion proporcionada. Como referencia, un modelo de 3,8 B en una GPU moderna suele ofrecer decenas de tokens por segundo, pero no hay mediciones publicadas para este checkpoint.
- Advertencia de muestreo: la model card recomienda temperatura en o muy cerca de 0; frameworks como Ollama usan 0,7 por defecto, lo que degrada las tareas de extraccion.

## Limitaciones y advertencias

- Ausencia de validacion: el repositorio no tiene descargas ni likes y no incluye evaluacion propia; no hay evidencia de que supere al modelo base `numind/NuExtract-v1.5`.
- Model card heredada: la mayor parte del README corresponde a NuExtract-v1.5 y no describe el ajuste del torneo, por lo que se desconoce que datos o hiperparametros se aplicaron.
- Riesgo de alucinacion: aunque el modelo prioriza la extraccion literal, en tareas de extraccion los modelos generativos pueden producir campos vacios, JSON mal formado o valores no presentes en el texto; la propia model card incluye utilidades para manejar JSON roto y salidas vacias.
- Sensibilidad a la temperatura: con temperaturas altas (por ejemplo, 0,7 por defecto en Ollama) la calidad de la extraccion se degrada notablemente.
- Dependencia de `trust_remote_code`: el tag `custom_code` obliga a ejecutar codigo remoto del repositorio, lo que implica un riesgo de seguridad que debe evaluarse antes de usarlo en produccion.
- Limitaciones de contexto: la model card recurre a prompting con ventana deslizante para documentos muy largos; no se garantiza una extraccion correcta en textos que exceden la ventana real del modelo.
- Idiomas: aunque se declara soporte multilingue, no se aportan metricas por idioma para este checkpoint concreto.
- Licencia: MIT, lo que permite uso comercial, pero el usuario debe verificar las condiciones del modelo base y del dataset de entrenamiento original, no documentadas aqui.
- Fecha de creacion futura (2026-09-28) y nomenclatura de torneo: conviene tratar el artefacto con cautela antes de integrarlo en cualquier flujo de produccion.
