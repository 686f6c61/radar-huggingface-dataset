## Resumen

Este repositorio contiene un adaptador LoRA (librería PEFT, versión 0.18.1) publicado por la organización `gradients-io-tournaments` en Hugging Face, obtenido mediante ajuste supervisado (SFT) con TRL sobre el modelo base `unsloth/Meta-Llama-3.1-8B-Instruct`. El identificador del repositorio incluye una marca temporal (20260928) y un UUID de ejecución, lo que indica que se trata de un artefacto generado automáticamente por un proceso de entrenamiento y no de un modelo publicado de forma manual y documentada.

La organización propietaria corresponde al sistema de torneos de Gradients (Subnet 56 de Bittensor), una infraestructura de entrenamiento descentralizado en la que distintas ejecuciones compiten entre sí. El repositorio acumula 0 descargas y 0 likes, y su model card es la plantilla por defecto de Hugging Face, con todos los campos marcados como `[More Information Needed]`, por lo que no se documenta el conjunto de datos, los hiperparámetros, la licencia ni los idiomas objetivo.

Su relevancia es, por tanto, la de un artefacto de investigación reproducible dentro de un pipeline de torneos, no la de un modelo listo para producción: se desconoce qué tarea concreta optimiza el ajuste y no se han publicado métricas. Cualquier evaluación seria requiere fusionar o cargar el adaptador sobre el modelo base y medirlo contra la versión Instruct original.

## Arquitectura y entrenamiento

El adaptador se aplica sobre Meta Llama 3.1 8B Instruct, un transformer decoder-only denso con atención por grupos (GQA), activaciones SwiGLU, RoPE y un vocabulario de 128 256 tokens, según la documentación pública del modelo base. Las etiquetas del repositorio confirman el uso de LoRA y de SFT mediante la librería TRL, además de haberse generado con PEFT 0.18.1. No se publica el rango (`r`), el `alpha`, las capas objetivo, la tasa de aprendizaje, el número de pasos ni el régimen de precisión empleado.

Tampoco hay información sobre el conjunto de datos de ajuste, su tamaño, su composición ni si se aplicaron etapas posteriores de alineación (DPO, RLHF). El repositorio incluye una etiqueta `base_model:adapter:/cache/models/8d7f663aaab4e5dd` que apunta a una ruta local de caché, señal típica de un pipeline automatizado en el que el adaptador se entrenó sobre una copia local del modelo base. El tamaño del repositorio (2,7 GB) es notablemente superior al de un adaptador LoRA convencional para un modelo de 8B, por lo que conviene inspeccionar los archivos antes de asumir que contiene únicamente pesos de adaptador.

## Capacidades

Las capacidades listadas proceden del modelo base y pueden haber sido alteradas, reforzadas o degradadas por el ajuste SFT, cuyo objetivo no se documenta:

- Generación de texto y conversación multi-turno en formato instruct.
- Seguimiento de instrucciones y tareas de resumen, reescritura y extracción.
- Generación de código y razonamiento matemático básico (capacidad nativa del modelo base de 8B).
- Tool calling / function calling: Llama 3.1 incorpora plantillas de llamada a herramientas en el modelo base; se desconoce si el ajuste las preserva.
- Uso en agentes y razonamiento multi-paso: posible vía el soporte de herramientas del modelo base, sin garantías tras el SFT.
- Capacidad multilingüe: el modelo base declara 8 idiomas; el idioma de los datos de ajuste no está disponible.
- Ventana de contexto larga: hasta 128 000 tokens según el modelo base.
- No dispone de visión ni audio (Llama 3.1 8B es exclusivamente de texto).
- No se anuncia modo de razonamiento explícito (`thinking mode`) ni decodificación especulativa propia.

## Casos de uso

Dado que no se documenta la tarea objetivo del ajuste, los casos siguientes son aplicaciones plausibles del modelo base que deben validarse empíricamente antes de usarse en producción:

- Evaluación comparativa de torneos: cargar el adaptador junto a otras variantes de la misma organización y medir con un conjunto de validación fijo para determinar qué ejecución del torneo rinde mejor en una tarea concreta.
- Asistente conversacional de dominio acotado: desplegar el modelo fusionado como servicio de chat interno con contexto largo (hasta 128 000 tokens) para consultas sobre documentación técnica extensa.
- Generación de código asistida: integrarlo en un IDE o en un bot de revisión de pull requests, siempre que se verifique que el SFT no ha degradado la capacidad de código del modelo base.
- Extracción estructurada de información: procesar contratos, informes o artículos largos y devolver JSON mediante plantillas de prompt, aprovechando la ventana de contexto del modelo base.
- Base para ajuste adicional: usar el adaptador como punto de partida de un segundo ciclo de LoRA/SFT con datos propios, ya que el formato PEFT permite apilar o reemplazar adaptadores sin tocar los pesos base.
- Prototipado en investigación sobre entrenamiento descentralizado: analizar qué hiperparámetros y datos producen adaptadores que superan al modelo Instruct original en un torneo concreto.
- Traducción y asistentes multilingües: explotar los 8 idiomas del modelo base, verificando antes el comportamiento en español y en los idiomas no cubiertos por los datos de ajuste.

Las cifras siguientes son estimaciones derivadas del tamaño del modelo base (8 000 millones de parámetros) y no mediciones del repositorio:

- Adaptador en safetensors: 2,7 GB de repositorio; requiere además el modelo base completo para poder inferir.
- Inferencia en bf16/fp16: aproximadamente 16 GB de VRAM solo para pesos, más caché KV (varios GB adicionales con contextos de 128 000 tokens).
- Inferencia en int8 (bitsandbytes): aproximadamente 9 GB de VRAM.
- Inferencia en 4 bits (NF4, AWQ o GPTQ): aproximadamente 5-6 GB de VRAM.
- GPU de centro de datos: A100 40 GB / 80 GB, H100 80 GB, L40S 48 GB; válidas para bf16 y para servicio concurrente con vLLM.
- GPU de consumo: RTX 4090 o 3090 (24 GB) para bf16 con contextos moderados; RTX 4080 (16 GB) y RTX 4070 Ti (12 GB) para cuantización de 4 u 8 bits; tarjetas de 8 GB solo con 4 bits y contextos cortos.
- Opciones de despliegue: transformers + peft (carga directa del adaptador), vLLM (soporte de adaptadores LoRA), TGI, y llama.cpp u Ollama tras fusionar el adaptador con el modelo base y convertir a GGUF.

## Limitaciones y advertencias

- La model card es una plantilla vacía: no hay información sobre datos, hiperparámetros, evaluación, sesgos ni uso previsto.
- La licencia no está declarada en el repositorio. El modelo base se rige por la Llama 3.1 Community License, que impone condiciones de atribución, requisitos de nomenclatura para productos derivados y restricciones para despliegues con más de 700 millones de usuarios mensuales. Al no declararse licencia propia, el uso comercial es jurídicamente incierto.
- El repositorio tiene 0 descargas y 0 likes, y presenta un tamaño (2,7 GB) anómalo para un adaptador LoRA de un modelo de 8B; conviene inspeccionar los archivos antes de usarlo.
- Al proceder de un torneo automatizado, no hay garantía de calidad, ni de que el ajuste mejore al modelo base; puede degradarlo en tareas generales por sobreajuste a un dominio desconocido.
- Riesgo de alucinación propio de un modelo de 8 000 millones de parámetros, especialmente en preguntas factuales, datos numéricos y referencias bibliográficas.
- No se conoce el idioma ni la composición de los datos de SFT, por lo que el comportamiento en español puede diferir del de Llama 3.1 8B Instruct original.
- La ventana de 128 000 tokens es una característica heredada del modelo base; no hay confirmación de que el ajuste conserve el rendimiento en contextos largos.
- No hay evaluación de sesgos, toxicidad ni robustez; no debería desplegarse en aplicaciones sensibles (salud, legal, finanzas) sin una evaluación propia.
- En producción conviene fijar la versión del adaptador y de PEFT (0.18.1), ya que el identificador incluye un UUID de ejecución que sugiere artefactos efímeros y no versionados semánticamente.
