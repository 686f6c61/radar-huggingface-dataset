# alexjmt1/Alx-1-400M

## Resumen

Alx-1-400M es un modelo de lenguaje de tipo GPT entrenado desde cero por el desarrollador independiente alexjmt1, con el objetivo específico de generar código Python. Cuenta con 405.256.192 parámetros reales (según los pesos en safetensors) distribuidos en 28 capas, 16 cabezas de atención y una dimensión de embedding de 1024. Su ventana de contexto es de solo 1024 tokens y fue entrenado con aproximadamente 156 millones de tokens en una única GPU T4 en precisión mixta fp16.

El modelo se presenta como un experimento de entrenamiento compacto más que como una alternativa de producción: el propio autor advierte que ha visto muchos menos tokens de los que corresponderían a una ejecución óptima en cómputo para su tamaño, por lo que la calidad del código generado es irregular. Es relevante ahora como ejemplo de modelo pequeño y reproducible para estudiar el efecto del subentrenamiento en modelos GPT orientados a código, y como base para experimentos de ajuste fino en entornos con recursos limitados.

La ficha se basa exclusivamente en la información publicada en Hugging Face: no hay pipeline declarado, no hay resultados de benchmarks y la licencia figura como "other" sin texto adicional, lo que limita cualquier uso comercial sin aclaración previa del autor.

## Arquitectura y entrenamiento

Se trata de un transformer decoder-only de estilo GPT con 28 capas, 16 cabezas de atención, dimensión de embedding de 1024 y una longitud de contexto de 1024 tokens. El tokenizador es el BPE de GPT-2 implementado con `tiktoken`, con el vocabulario rellenado hasta 50304 entradas. El modelo se entrenó desde cero, no como ajuste fino de un modelo existente, en precisión mixta fp16 sobre una única GPU T4, con un total aproximado de 156 millones de tokens y una pérdida de validación final de 1,3330.

Los datos de entrenamiento proceden de cuatro conjuntos publicados en Hugging Face: `iamtarun/python_code_instructions_18k_alpaca`, `flytech/python-codes-25k`, `Vezora/Tested-143k-Python-Alpaca` y `codeparrot/codeparrot-clean`. No se documenta el uso de RLHF, DPO ni ninguna otra etapa de alineación, ni innovaciones técnicas como decodificación especulativa o atención lineal. El formato de prompt es `Task:\n<instruction>\nCode:\n`.

## Capacidades

- Generación de código Python a partir de instrucciones en inglés, con el formato de prompt `Task:\n<instruction>\nCode:\n`.
- Generación de texto genérico limitada, derivada del entrenamiento sobre código y datos de instrucciones.
- No se documenta soporte de tool calling ni de function calling.
- No se documenta soporte de agentes ni de razonamiento multi-paso.
- Capacidad multilingüe limitada al inglés (idioma declarado: `en`).
- No dispone de modo de razonamiento explícito (thinking mode), visión ni audio.
- No se documenta una plantilla de chat conversacional; el uso previsto es de completado de instrucciones de una sola vuelta.

## Casos de uso

- Prototipado rápido de funciones Python sencillas: el modelo puede generar borradores de funciones a partir de una instrucción breve, útiles como punto de partida que el desarrollador revisa y corrige.
- Experimentación académica sobre subentrenamiento: sirve para estudiar cómo afecta un presupuesto de 156 millones de tokens a la calidad del código en un modelo de 405 millones de parámetros.
- Base para ajuste fino con recursos limitados: al caber en una sola GPU consumer y publicarse en fp16, puede reentrenarse o ajustarse con LoRA en entornos pequeños para tareas de código acotadas.
- Generación de ejemplos y tests unitarios simples: puede producir fragmentos de código de prueba para validar pipelines de CI/CD, siempre con revisión humana obligatoria.
- Docencia y demostraciones de entrenamiento desde cero: su receta completa (tokenizador, datasets, hiperparámetros básicos) permite reproducir el flujo en un curso o taller.
- Evaluación comparativa de modelos pequeños de código: como referencia de línea base en estudios que midan la relación entre tokens de entrenamiento y calidad de generación.
- Generación de snippets para autocompletado en editores, únicamente en escenarios no críticos y con validación posterior, dado el riesgo de código incorrecto.

## Benchmarks y rendimiento

No se han publicado resultados de benchmarks en la informacion disponible. El único dato de rendimiento publicado es la pérdida de validación final de 1,3330, que no es comparable directamente con métricas como HumanEval, MMLU o GSM8K.

## Requisitos de hardware

- VRAM estimada para inferencia: aproximadamente 1,6 GB en fp16 (405 millones de parámetros × 2 bytes) y unos 3,2 GB en fp32, antes de overhead de activaciones y caché KV.
- GPU recomendadas: el autor entrenó en una NVIDIA T4; para inferencia es suficiente cualquier GPU con al menos 4 GB de VRAM.
- Cabe en GPU consumer: sí, en tarjetas como RTX 3060, RTX 4060, RTX 4090 y equivalentes con 6 GB o más de VRAM; también puede ejecutarse en CPU para pruebas.
- Opciones de despliegue: el repositorio incluye el módulo `alx_model` con las funciones `load_alx1` y `ask`, pensado para PyTorch y `safetensors`. No se documenta integración con vLLM, llama.cpp, Ollama o TGI, ni existen pesos GGUF publicados.
- Latencia y throughput estimados: no disponibles.

## Limitaciones y advertencias

- El autor advierte explícitamente que el modelo ha visto muchos menos tokens de los óptimos para su tamaño, por lo que genera código verosímil pero a menudo incorrecto o incompleto.
- Ventana de contexto muy reducida (1024 tokens), insuficiente para archivos de código medianos o conversaciones multi-turno.
- Solo soporta inglés; no hay evidencia de capacidad en castellano u otros idiomas.
- Licencia "other" sin texto publicado: no se puede asumir uso comercial permitido; es necesario contactar con el autor o revisar las licencias de los datasets de origen (`codeparrot-clean` incluye código de GitHub bajo licencias diversas).
- Riesgo elevado de alucinación en APIs, nombres de funciones y librerías, dado el escaso entrenamiento.
- No hay etapa de alineación documentada (RLHF/DPO), por lo que puede reproducir sesgos presentes en el código de GitHub.
- Ausencia de benchmarks y de pipeline declarado: no hay validación independiente de su calidad.
- Sin soporte documentado de tool calling, agentes ni plantilla de chat, lo que limita su integración en aplicaciones conversacionales.
