**Radar HuggingFace Dataset** is an open, living, versioned dataset of the
HuggingFace open source ecosystem. Thousands of models are published to the
hub every day, and its API can only tell you how a model is doing *right
now*; here you'll find — three times a day — a curated, enriched snapshot of
everything worth paying attention to: what gets published, who publishes it,
under which license, what traction it really gets, which formats it ships in,
how many parameters it actually has — and which models quietly disappear.

It is generated by **[HF//RADAR](https://radar-huggingface.686f6c61.dev)**, a
radar that analyzes trending models and writes a technical model card in
Spanish for each one. This repo is its data output: normalized per-model
metadata + its model card, with an auditable history.

## The research goal

HuggingFace's API answers questions about the present. This dataset exists to
answer better questions:

- **What gets published and by whom** — which organizations dominate the hub,
  with which licenses, sizes and distribution formats (GGUF, MLX,
  safetensors...).
- **What has real traction** — downloads and likes over time windows, not
  just the all-time totals that favor old models.
- **What disappears** — the hub never announces removals. Every withdrawn
  model stays here, flagged (`removed`, `removed_at`): the ecosystem's
  tombstones.
- **How it all evolves** — updated three times a day with every version
  numbered, the release history is a time series of the OSS ecosystem that
  cannot be reconstructed after the fact from the API.

On top of that, every model ships with a **technical model card in Spanish**
(what it does, what it's for, requirements, limitations), because hub
documentation is overwhelmingly English and uneven in quality.

This is not a mirror of the hub: it is a **curated layer** — only models
verified as open source with a minimum of useful information.

## How `data/` is structured

One folder per author (HF organization or user) and, inside, **two files per
model**: the `.json` with the metadata and the `.md` with the model card.

```
data/
├── qwen/
│   ├── qwen3.8-27b.json          # structured metadata (SCHEMA.md)
│   ├── qwen3.8-27b.md            # model card (Spanish)
│   ├── qwen3.8-27b-fp8.json
│   └── qwen3.8-27b-fp8.md
├── meta-models/
│   ├── muse-glimmer-30b.json
│   └── muse-glimmer-30b.md
└── ... (thousands of authors)
```

- The folder name is the lowercased author; the file name is the model.
  Together they form the model's unique `slug` (`author-name`).
- If two distinct models collide on name (it happens: re-uploads that only
  differ in capitalization), the newer one gets a `-2`, `-3`... suffix.
- The `.json` follows [SCHEMA.md](SCHEMA.md) (version 1): classified license,
  real parameter counts, distribution formats, benchmarks, KPIs, access and
  removal flags.
- The `.md` is the card generated by the radar from the model card and web
  sources.
- `index.json` (repo root) is the light manifest: every entry with its key
  fields, for discovery without downloading the whole tree.

## How updates work

A worker on the radar's server runs **three times a day** — 06:00, 14:00 and
22:00 (mainland-Spain time) — and does:
export from the database → incremental writes (only what changed gets
rewritten) → structured commit → push. The CI validates every push, publishes
the updated bulk and creates the corresponding numbered release.

**If a folder has some KPIs today and they go up tomorrow, does it update?**
**Yes, in place, in the same file.** That model's `data/author/model.json`
gets rewritten with the new `likes`, `downloads_30d`, `trending_score`... and
the worker's commit logs it as modified (`~`). No new file, no new folder:
the tree always reflects **the most recent state**.

Yesterday's values are not lost:

1. In the **git history** (every commit is an auditable diff), and
2. in the **numbered releases** (`v1.0.0`, `v2.0.0`...), immutable snapshots
   of the complete dataset at that moment.

Models withdrawn from HF are **not deleted**: their file stays with
`removed: true` and the removal date. A file is only deleted if the model is
removed from the radar's database (exceptional case).

## Quickstart

```bash
# A single model (metadata)
curl -s https://raw.githubusercontent.com/686f6c61/radar-huggingface-dataset/main/data/qwen/qwen3.8-27b.json
```

```python
# The whole dataset with pandas (bulk, card included)
import pandas as pd
url = "https://github.com/686f6c61/radar-huggingface-dataset/releases/download/latest/models.jsonl.gz"
df = pd.read_json(url, lines=True)
```

```sql
-- DuckDB straight over the bulk (no download)
SELECT author, COUNT(*) AS models
FROM read_json('https://github.com/686f6c61/radar-huggingface-dataset/releases/download/latest/models.jsonl.gz', format='newline_delimited')
GROUP BY author ORDER BY models DESC LIMIT 10;
```

## Versioning

One release per update with new data, with the time slot encoded in the
version itself:

| Run (Spain time) | Slot | Bump | Example |
|---|---|---|---|
| 06:00 | Morning | major | `v3.0.0` |
| 14:00 | Afternoon | minor | `v3.1.0` |
| 22:00 | Night | patch | `v3.1.1` |

So `v14.2.1` is the **night export of day 14** since the dataset started.
Releases are **immutable**: to reproduce an analysis, pin to a specific
version. *Format* changes are announced separately by bumping `schema` and
documenting them in CHANGELOG.md.

- **`latest` release** (floating): always points to the most recent export.
  Its asset URLs never change — that's the one you want for recurring
  consumption.
- **Structured commits** (`data: +12 ~140 -1`): added, modified and deleted
  files in each run.
